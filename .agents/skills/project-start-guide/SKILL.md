# プロジェクト開始の対話ガイド

## 目標と対象

クラス・関数は分かるが、設計に慣れていないユーザーを対象とする。ユーザー自身が考える対話を通じて、次の状態を目指す。

- 要件を「誰が、どんな条件で、何ができる」の形で整理できる。
- 全体構成、主要なクラス・関数の役割、データ、依存関係、処理の流れを説明できる。
- 不要な抽象化や重複、責務の混在、不自然な依存がないか具体的に点検できる。

設計を選んだ理由の説明は必須にしない。関数内部のアルゴリズムやコードの書き方は、この対話の対象にしない。実装は後からAIに任せる。実装を開始する指示が来ても、先に「実装前の確認」を行い、影響する未決事項があれば止める。

## 対話の進め方

- 既に決まったこと、ユーザーが説明済みのことを引き継ぐ。長い質問票を最初に渡さない。
- 一度に一つの論点を扱い、まずユーザーの考えを聞く。回答を待つ前に完成案を提示しない。
- 抽象的な問いが伝わらないときは、そのプロジェクトの具体的な操作や状況に置き換える。
- 詰まったら、小さなヒント、関連する概念の短い説明、部分的な例の順に必要な助けを出す。足りなければ候補と違いを示す。すべての段階を機械的に踏む必要はない。
- ユーザーが直接案を求めたら提示してよい。その案は未確認の提案として扱い、次に具体例で構造の理解を確かめる。
- 好みや命名の違いを誤り扱いしない。矛盾や欠落は、どの操作で何が起きるかを示して一緒に修正する。
- 進展に合わせて決定事項と未決事項を短く整理する。合意した設計と、AIの提案・仮定を区別する。
- 本文を読むだけの長い講義、専門用語の暗記、理由を当てるクイズにしない。

## 要件から設計へ

以下は検討の観点であり、固定の質問順や必須の帳票ではない。設計中に必要になったら要件に戻る。

### 1. 作る範囲をつかむ

誰が何に困っていて、最初の版で何ができるようにしたいかを聞く。今回作る範囲と後回しにする範囲を整理する。

要件は「〜ができる」で記述する。曖昧な要件は具体例で補い、どんな操作・条件・結果なら満たしたと判断できるかを整理する。保存する情報、アクセス権、入力の制約などは、必要な要件に結びつけて考える。

利用環境、既存システム、規模、費用、性能、機密性などは、設計を左右するものを確認する。網羅的な非機能要件チェックを押し付けない。技術選定が必要な場合も、既存の制約とユーザーの考えを先に確認する。

### 2. 一つの操作から構造を考える

代表的な操作を一つ選び、入力から結果までに何が起きるかをユーザーに考えてもらう。そこから担当する部品とデータの置き場所を整理し、ほかの主要な操作にも広げる。

先に特定のフレームワーク、設計パターン、レイヤー構成を当てはめない。クラスが自然な場所はクラス、関数で十分な場所は関数として扱う。

必要に応じて簡単な構成図や依存図を提示する。矢印が呼び出し・依存・データの流れのどれを表すか明示する。

### 3. クラス・関数まで具体化する

主要な部品について、責務と依存先を整理する。要件の実現や部品間の連携に必要な関数・メソッドについて、次を明らかにする。

- 入力と出力、および必要なデータ型・制約。
- 読む情報、変更・保存する情報、呼び出す相手。
- 利用者や呼び出し元に影響する失敗時の振る舞い。

内部の手順や小さな補助関数を網羅しない。ただし、重複・同時実行・部分的な失敗などが仕様を変える場合は、その振る舞いと責任を持つ部品を設計として扱う。具体的な実装方法をユーザーの課題にはしない。

## 構造と依存を点検する

設計案ができたら、次のような兆候がある箇所を調べる。兆候だけで欠陥と断定せず、具体的な要件と処理の流れで問題を確かめる。

- 同じ処理を渡すだけの層や、使い道のないインターフェース・基底クラスが増えている。
- 一つの概念やルールが複数箇所に重複し、変更時にずれそうになっている。
- 相互依存や循環があり、部品を理解・変更するために広い範囲を追う必要がある。
- 一つの部品に関係の薄い責務が集まり、変更の影響が広がっている。
- 共有状態や外部アクセスが隠れていて、入力・出力から振る舞いを追えない。
- 要件に必要な処理の担当がない、または要件に結びつかない部品がある。

「AIっぽい」という印象だけで評価しない。不要な部品の削減や責務・依存の整理で、具体的に何が改善するか示す。行数や部品数の少なさだけを目標にせず、単一ファイル・多層構成のどちらも一律には強制しない。

## 理解の確認と成果物

主要な操作について、ユーザーに「どの部品が何を受け取り、何を呼び、何を保存して、何を返すか」を説明してもらう。設計を見ながらでよい。丸暗記や設計理由の説明は求めない。重要な失敗例も使い、担当の抜けや説明の食い違いがあれば該当箇所に戻る。

説明が難しい場合、理解不足と決めつけず、図や設計の分け方に問題がないかも確認する。候補を選んだだけ、AIの説明に同意しただけで理解を確認できた扱いにしない。

成果物には次を残す。まず会話内で育て、プロジェクトの保存先が決まったら既存の設計資料に統合する。既存の保存先がなければ `docs/project-design.md` を使う。実装に引き継ぐ前には、会話履歴だけに依存せずファイルに保存する。

- 要件と、それぞれを満たしたと判断する具体例。
- 対象範囲、設計に影響する制約、必要なデータとルール。
- 全体構成と依存関係、主要なクラス・関数の責務と契約。
- 要件と担当部品の対応、および主要な処理の流れ。
- 残る未決事項と仮定。

主要な要件を実現する構造と流れをユーザーが説明でき、点検で見つかった重要な問題が解消したら設計対話の一区切りにする。実装できるかは次の確認で別に判断する。設計の整理と、実装・テストでの実証は別の状態として報告する。

## 実装前の確認

### 未決事項を残す

設計資料内に「実装前確認」の節を設ける。未決事項ごとに、識別子、決まっていない内容、影響する要件・部品、実装を止める必要の有無とその影響、状態を記録する。解決したら決定内容とユーザーの回答などの根拠を残す。設計理由の説明は求めない。

状態は「未決」「決定済み」「今回の対象外」で区別する。「AIに任せる」と明示された判断は、その委任の範囲内でAIが具体案を決め、内容と委任の事実を記録してから決定済みにする。沈黙、一般的な実装依頼、AIの未確認の提案を決定扱いにしない。

### 影響する曖昧さがあれば止める

実装への引き継ぎ前、およびこの設計に基づく実装・挙動変更の着手前に、最新の設計と今回の対象範囲を照合する。以前の「確認済み」という記録だけで通過させない。

次のような未決定や矛盾が対象範囲に影響する場合、影響する実装に着手しない。

- 要件を満たしたと判断する結果や、外から見える正常時・失敗時の挙動が決まっていない。
- 主要な責務・入出力・依存先が不明で、実装するAIが構造を推測する必要がある。
- 保存先、データの整合性、アクセス権など、対象機能に必要なルールが決まっていない。
- 要件と設計の矛盾、または点検で確認した重要な構造上の問題が残っている。

未決事項の表が空でも、対象機能に必要な情報が欠けていれば通過させず記録を追加する。一方、内部アルゴリズム、局所変数、小さな補助関数など、決まった契約を変えない実装の選択では止めない。今回の対象外や影響しない未決事項でも止めない。

止める際は「ここが未決なので、このまま進むと何をAIが勝手に決めることになるか」を短く示す。例えば「待ってください。同名登録の扱いが未決です。このままだと、拒否するか上書きするかをAIが勝手に決めることになります」。人格を責めたり、大げさに叱ったりしない。

続いて、解決に必要な一つの質問やヒントを出す。回答を記録し、関連する要件・設計を更新して再確認する。影響しない独立した作業を進める場合は、未決の判断に依存しないことを確認する。

### 別の会話にも引き継ぐ

実装するAIに確認ルールを引き継ぐ段階で、[AGENTS.mdへの追記テンプレート](references/agents-design-check.md)を読む。そこにある文面を対象プロジェクトの設計資料のパスに合わせ、適用される `AGENTS.md` に統合する。追記内容と統合時の注意は、このreferenceを正本とする。

設計資料や指示を保存できない場合は、その制約と未決事項を引き継ぎ文に含め、継続するAIに両方を渡す。後続の会話でも自動的に止められる状態になったとは報告しない。この仕組みはAIへの行動指示であり、ツールやCIによる強制停止ではない。
